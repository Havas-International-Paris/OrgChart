# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Internal org chart tool for Havas International: an editable spreadsheet (left) and a visual org chart (right) on one screen, backed directly by Supabase (Postgres + Auth + Realtime + Storage) with no custom backend server. Supports multi-reporting (an employee can have several managers, one flagged primary), per-employee client/mission assignments with %ETP, and multiple independent org charts within the same project.

## Commands

```bash
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # tsc -b (typecheck) && vite build — this is the primary correctness check, run it after any change
npm test          # vitest run — the pure-logic unit tests
npm run test:watch
npm run test:e2e  # playwright test — browser end-to-end suite
npm run gen:types # regenerate src/lib/database.types.ts from the live schema
npm run lint      # oxlint
npm run preview   # preview a production build
```

`npm run build` (which runs `tsc -b` over three TS projects: `src`, the Vite/Vitest configs, and `e2e`) plus `npm test` are the two checks to run after any change; `npm run test:e2e` when the change is user-visible. Coverage is deliberately narrow — see "Known issues" for exactly what it does and doesn't reach.

**The E2E suite is split into three Playwright projects** (`playwright.config.ts`) so it stays useful without credentials. `public` needs no login and always runs. `setup` signs in through the real login form and provisions a **throwaway `org_charts` row**; `authenticated` reuses that session and operates only inside that chart, so destructive specs never touch real data — this is what unblocked E2E at all, since the same Supabase project backs local dev and production. `cleanup` is attached as the setup project's `teardown`, so a failed run still deletes the throwaway chart (by the `E2E throwaway ` name prefix, which also sweeps up charts stranded by an earlier crash, and can never match a human-created one) and removes the saved session token. Without `.env.test.local` (see `.env.test.local.example`) the authenticated specs **skip rather than fail**, and the run still exits 0. `webServer.reuseExistingServer` is on deliberately: the normal state of this repo is a dev server already running for manual testing, and tearing it down mid-session is hostile.

`e2e/` needs its own `tsconfig.e2e.json` with `moduleResolution: bundler`: it can't join `tsconfig.node.json`, whose `nodenext` resolution demands explicit `.js` extensions on relative imports that Playwright's own loader neither needs nor expects.

The dev server requires `.env.local` (copy from `.env.example`) with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from a Supabase project that has had the migrations in `supabase/migrations/` applied (see README.md for the full setup sequence — order matters, `0004` in particular is easy to forget and silently breaks realtime). Without `.env.local`, the app renders a "Configuration Supabase requise" screen instead of crashing (see `isSupabaseConfigured` in `src/lib/supabaseClient.ts`).

## Architecture

**Data flow: services → hooks → components.** `src/services/*` are thin wrappers around `supabase-js` calls (one file per table). `src/hooks/use*` each own one table's full dataset: fetch on mount, subscribe to Postgres changes, and re-`fetch()` (not incremental patching) on any change. Because the whole org is a few hundred rows at most, every hook loads its entire table and consumers filter/derive in memory (e.g. `useReportingGraph().managersOf(employeeId)`, `useAssignments().totalEtpOf(employeeId)`) rather than querying per-employee. Don't add pagination or per-entity fetching without a real scale reason.

**Realtime channel names must be unique per mount.** Every hook subscribes with `` `table-changes-${crypto.randomUUID()}` `` rather than a fixed string. A fixed channel name breaks the moment two consumers of the same hook are mounted at once (e.g. `EmployeeGrid` and `OrgChartView` both call `useEmployees()`) or React StrictMode double-mounts in dev — Supabase's realtime client throws `cannot add postgres_changes callbacks ... after subscribe()` because the second `.channel(sameName)` call returns the already-subscribed channel object. If you add a new data hook, follow this pattern.

**`employees`/`reporting_relationships`/`assignments`'s `postgres_changes` subscriptions are deliberately unfiltered** (no `filter: org_chart_id=eq.X`), relying on `refresh()`'s own query — which *is* scoped by `org_chart_id` — to keep displayed data correct. This looks wasteful (every mounted consumer refetches on any change to the table, across every org chart, not just its own) but is deliberate: a filter on a non-primary-key column like `org_chart_id` silently drops DELETE events. Postgres's default replica identity only ships primary-key columns in a DELETE's WAL entry, so Realtime can't evaluate a non-PK filter and never delivers the event to filtered subscribers — INSERT/UPDATE were never affected since the full new row is always available. Hit as a real bug (deleting an employee from the grid left a stale card in the chart, and vice versa, until a manual reload) and initially "fixed" with `alter table ... replica identity full` (`0012_realtime_delete_replica_identity.sql`) — that turned out **insufficient on its own** (verified live, the bug still reproduced after applying it), so the filter was removed entirely instead. The migration is harmless to leave applied but isn't what actually fixes this — don't reintroduce a `filter: org_chart_id=eq...` on these three subscriptions without re-verifying DELETE propagation live in the browser, not just trusting `REPLICA IDENTITY FULL` to be enough.

**Multi-reporting model.** `reporting_relationships` rows have `employee_id`, `manager_id`, `is_primary`. At most one primary manager per employee (partial unique index in `0001_init_schema.sql`). Primary edges form the tree used for the automatic elk layout (`src/components/chart/layoutEngine.ts`); secondary edges are drawn afterward as a dashed overlay using the positions elk already computed — they never participate in layout. `useVisibleGraph` walks the primary-edge tree from roots (employees with no primary manager) down through whichever nodes are in the `expandedNodeIds` set.

**Multiple independent org charts share the same tables.** `org_charts` (`0009_org_charts.sql`) is the scoping table; `employees`, `reporting_relationships`, and `assignments` each carry a required `org_chart_id`, and every hook/service touching those three tables takes `currentOrgChartId` (from `selectionStore`) as a parameter — `useEmployees(currentOrgChartId)`, `useReportingGraph(currentOrgChartId)`, `useAssignments(currentOrgChartId)`. `clients_missions`, `job_titles`, and `departments` stay global/unscoped catalogs shared across every chart. Uniqueness constraints (`uq_one_primary_manager`, `uq_employee_client_mission`) and the cycle-check trigger below are all re-scoped to include `org_chart_id`, so two charts can never interfere with each other even with identical employee/relationship shapes. Switching charts (the selector in `AppShell.tsx` → `setCurrentOrgChartId`; `OrgChartManagerModal.tsx` handles create/rename/duplicate/delete) resets every chart-relative field in `selectionStore` (selection, expand/focus sets, search, assignments modal). `duplicate_org_chart(source_id, new_name, new_short_label)` (a Postgres RPC) deep-copies one chart's employees/relationships/assignments into a new chart via a temp id-remap table; `clients_missions` references are copied as-is since that catalog is shared.

**Cycle prevention is deliberately doubled.** Client-side `wouldCreateCycle` (in `useReportingGraph.ts`) does a BFS from the proposed manager upward through existing edges before any write is attempted, so the UI can grey out invalid choices live. `0003_cycle_check_function.sql` adds the same check as a Postgres trigger with a recursive CTE, because the client-side check alone leaves a race window between two simultaneous users. Both must stay in sync if the reporting model changes.

**Undo/redo is identity-stable, and that is why there is no id indirection.** Every `restore*` function in `src/services/*` re-inserts a captured row under its **original id** (`restoreEmployee`, `restoreRelationship`, `restoreAssignment`, `restoreClientMission`, `restoreJobTitle`, `restoreDepartment`), instead of creating an equivalent row and letting Postgres mint a new UUID. So a command recorded at t0 can close over a plain string id and still be correct after any number of undo/redo cycles. This replaced `idBox.ts` + `idRegistryStore.ts` (a mutable `{id}` box per entity plus a global registry, ~3 files of machinery) which existed solely to follow entities through delete/recreate. **If you add a mutator with an undo, capture the row and restore it — never re-create it.** `restoreEmployee` deliberately restores the whole row, so a photo, its crop and any manual `sibling_order` survive an undo; the old create-based path silently dropped them. `created_at`/`updated_at`/`created_by`/`updated_by` are omitted on purpose — the `set_updated_at`/`set_audit_fields` triggers own those.

**Cross-view state lives in one Zustand store**, not component state: `src/stores/selectionStore.ts` holds `selectedEmployeeId`, `searchQuery`, `expandedNodeIds`, `focusedNodeIds`, and `assignmentsEmployeeId`. `EmployeeGrid` and `OrgChartView` both read/write it so that clicking a row centers the corresponding chart node (and vice versa), and so search highlights/auto-expands ancestors in the chart while filtering the grid — `EmployeeGrid`'s own `sortedEmployees` memo does the text filtering directly against `searchQuery`, there is no grid-library quick-filter feature involved. `AssignmentEditorModal` is rendered once at the `AppShell` level (not inside the grid or the chart) and opens based on `assignmentsEmployeeId`, so either view can trigger the same modal instance.

**A second, deliberately separate Zustand store holds per-browser UI preferences**: `src/stores/uiPreferencesStore.ts` (`gridDensity`, `splitFraction`) is wrapped in zustand's `persist` middleware, writing to `localStorage` — unlike everything in `selectionStore.ts`, which is in-memory only and explicitly wiped on every org-chart switch. These preferences never touch Supabase, so one person's density/split choice can never leak to anyone else, at the cost of not following a user across browsers/devices (an explicit, accepted tradeoff — see git history if a per-account version is ever wanted). `src/components/grid/editableGridLogic.ts`'s `densityClasses(density)` is how all 4 left-panel grids render themselves densely — just two Tailwind class strings and an avatar-size number, now that none of them go through a grid library's own theming API. `AppShell.tsx`'s grid/chart split divider is a plain `setPointerCapture`-based drag (same pattern as `PhotoEditorModal.tsx`'s pan/zoom), clamped to `[0.2, 0.75]`.

**The drag-to-reorder geometry is pure and unit-tested**, in `src/components/chart/siblingReorderGeometry.ts` — extracted from `OrgChartView`'s two drag handlers, which are now thin glue. `computeReorder` decides what a released drag means (snap back, or which `sibling_order` rows to write, including the backfill-the-whole-group-on-first-touch invariant); `findDisplacementTargets` decides who to highlight mid-drag. Both share `isWithinGroupSpan`, so a drop can never be accepted at a position the live feedback already rejected — keep that shared, it's the reason the two agree. This is the logic that took five debugging passes in backlog item 25; while it lived inside a `useCallback` it could only be checked by hand, one drag at a time in a browser.

**`OrgChartView.tsx` is composition only** (~195 lines); each concern is a hook beside it, and they must be called in this order because each feeds the next: `useChartData` (datasets + every derived lookup) → `useChartVisibility` (expand/collapse, then focus mode on top) → `useChartActions` (mutations + the UI state they open: link modal, photo editor, selected edge) → `useChartNodes` (elk layout, node/edge arrays, live drag, hover) → `useChartViewport` (default expansion, auto-fit, panning to a selection). `useChartData` destructures its three data hooks field by field rather than spreading them — all three return a `loading` and an `error`, so spreading lets the last one silently win.

`useChartNodes` is the big one (~435 lines) and is deliberately not split further: `flowNodes`, `isDraggingRef`, `displacementTargetIds` and the two drag handlers are one unit, and separating them means passing setters between hooks, which is exactly what reintroduces the infinite render loop and the drag flicker documented below.

**elk lays out every employee, not just the currently-visible ones — and does it asynchronously.** `useChartNodes`'s `layoutedNodeById` is `useState` populated by a `useEffect` that calls `layoutWithElk` (elkjs, replacing dagre 2026-07-30) over the *entire* `employees`/`primaryEdges` set, guarded by a `layoutRequestIdRef` so a stale in-flight response can't overwrite a newer one — unlike dagre, `elk.layout()` returns a Promise even for the in-thread `elk.bundled.js` build used here, with no synchronous escape hatch. This effect depends on nothing else — not `expandedNodeIds`, not focus mode, not hover/selection/search/the dept filter. A second, cheap memo filters that position map down to whichever employees are currently visible and layers on per-render styling (dimming, chain highlight, selection). This split exists because elk (like dagre before it) is a global, non-incremental layout — re-running it on a smaller or larger node set reflows *every* node's x/y, not just the ones that appeared or disappeared, so a naive "layout only what's visible" approach makes collapsing a team or using focus mode visibly shift unrelated, still-visible cards (a real regression hit and fixed once already, under dagre). Keep this split if you touch this code: anything that changes which cards render belongs in the second memo, never the first. No separate "layout loading" flag exists for the async gap: `computedNodes`'s per-employee `if (!baseNode) return []` and `useChartViewport`'s existing `computedNodes.length === 0` fitView gate already tolerate the map being momentarily empty or missing a brand-new node, the same way they already tolerate the Supabase fetch itself. `layoutEngine.ts`'s ELK options are tuned to match dagre's old geometry: `elk.layered.spacing.nodeNodeBetweenLayers`/`elk.spacing.nodeNode` mirror dagre's `ranksep`/`nodesep`, `elk.padding: 0` cancels elk's default graph padding (dagre had none), and `elk.layered.considerModelOrder.strategy: NODES_AND_EDGES` keeps a manager's children contiguous on their rank — without it, elk's crossing-minimization can interleave one manager's team with an unrelated sibling's cards (confirmed live), which also breaks the sibling-reorder width measurement below. **`applySiblingOrder`'s subtree-shift anchors to the subtree's own bounding-box center, not the parent's own old→new delta** — the latter was dagre's exact approach and silently relied on dagre's habit of centering a parent over its children, which elk does not guarantee (a manager's card can land outside its own team's span). Anchoring to the subtree's own measured span instead is what makes the reorder correct regardless of which layout engine is underneath; get this wrong and a reordered manager's whole team can end up overlapping a neighboring sibling's cards even though the manager's own card looks right.

**Reassigning a reporting relationship to a new manager is a native React Flow reconnect drag, not the old hand-rolled grip** (replaced 2026-07-30, backlog items 32/33 done together). Every card renders one `Handle` per relationship it's party to — `EmployeeNode.tsx`'s `incomingHandleIds`/`outgoingHandleIds` (computed in `useChartNodes.ts`'s styling pass) — each handle's `id` is the underlying `reporting_relationships` row's own id, used identically as both the manager's outgoing (source, Bottom) handle id and the employee's incoming (target, Top) handle id on the corresponding edge, so no separate id scheme was needed. Handles on each side are spread evenly (`((i+1)/(n+1))*100%`) in the order of each *neighbor's* already-laid-out x — a manager with several children gets one handle per child spaced along the bottom edge, so a reconnect drag can grab and drop one specific relationship instead of every edge on that side converging on one shared point. A node with zero current relationships on a given side still renders exactly one synthetic fallback handle on that side (`` `${employeeId}-out` `` / `` `${employeeId}-in` ``) — real relationship-backed handles only exist for relationships that already exist, but a candidate node needs *some* connectable handle to be a valid drop target: the outgoing fallback so a manager-to-be can receive their first-ever report (via reassignment or a fresh connect, below), the incoming fallback so an employee with no manager yet can receive one the same way. Every edge sets `reconnectable: 'source'` (`useChartNodes.ts`), restricting reconnect drags to the manager end only — the employee/target end is never draggable, matching the deleted grip's exact constraint.

**A second, separate native gesture — drag-to-connect — creates a brand-new relationship between two cards already visible on the chart**, added the same day as a follow-up once reconnect was confirmed working by hand — this session's browser automation cannot drive either gesture (see [[feedback_browser_testing_gotchas]]), so unlike reconnect, drag-to-connect is wiring-verified only (handle structure and fallback ids confirmed correct via DOM audit) and still needs the user's own hands-on check. This is additive, not a replacement: the "+" popover's "Rattacher un existant…" (`LinkExistingEmployeeModal`) stays the only way to link an employee not yet anywhere on the chart, since a drag needs both endpoints already rendered. `OrgChartView.tsx` wires `onConnect` to `useChartActions.ts`'s new `handleConnect(managerId, employeeId)`, which reuses `computeDropValidity` unchanged (the existing "already a manager" check doubles as duplicate-link prevention) and the same primary/secondary rule every other link-creation path uses (first manager is primary, every one after is secondary/dotted). Direction is always top-down — the user drags from a manager candidate's own outgoing (Bottom/source) handle to the employee's incoming (Top/target) handle — enforced for free by React Flow's default `connectionMode: 'strict'`, which only ever lets a connection *start* from a source-type handle, so the resulting edge's source=manager/target=employee convention can't be inverted regardless of which card the user grabs first. `onConnectStart`/`onConnectEnd` reuse the exact same `handleReconnectStart`/`handleReconnectEnd` callbacks reconnect uses (both gestures cross unrelated cards mid-drag the same way, so both need the same hover-suppression). `OrgChartView.tsx` wires `onReconnect` to `useChartActions.ts`'s `handleReconnect(edgeId, newManagerId)`, which resolves the id back to the relationship row and defers to the pre-existing `handleReassignManager` (unchanged: reassigning only ever updates `manager_id` via `reportingService.updateRelationshipManager`, `is_primary` is untouched — confirmed by reading the full chain before this rework, so there was no new primary/secondary decision to design). `isValidConnection` on `<ReactFlow>` wraps the existing `computeDropValidity`/`wouldCreateCycle` chain unchanged. Live green/red drop-candidate feedback moved from the old grip's imperative `style.outline` DOM mutation into `EmployeeNode.tsx` reading React Flow's own `useConnection()` store (`{inProgress, isValid, toNode}`) — ordinary render state instead of manual DOM writes. `isReassigningEdgeRef` (suppresses hover-driven re-dimming mid-drag, see the mouseLeave-debounce note above) is unchanged in mechanism, just retargeted from the old edge-level `onDragStateChange` callback to `<ReactFlow>`'s `onReconnectStart`/`onReconnectEnd`. Handle positions are computed strictly *after* elk's layout finishes, purely from final x-coordinates — never fed back into elk as layout input (elk does support hierarchical ports for that, deliberately left as a possible future optimization rather than attempted here).

**Hovering a link highlights its own two endpoint cards plus the link itself** (added 2026-07-30, same session as the handle work above) — deliberately narrower than hovering a CARD, which highlights the whole ancestor/descendant chain via `useReportingChain`. The point here is disambiguation: when a manager has several reports, their links can visually overlap, and the user needs to see at a glance exactly which manager/employee pair one specific line connects before dragging it. `ReportingEdge.tsx`'s existing invisible hit-test path (already used for click-to-select) gained `onMouseEnter`/`onMouseLeave` calling `data.onHoverChange`. `useChartNodes.ts` owns a separate `hoveredEdgeId` state (deliberately independent of `hoverEmployeeId`/`activeEmployeeId` — hovering a link must never trigger the full chain highlight), debounced the same way as node hover (`clearEdgeHoverTimeoutRef`, 120ms) since overlapping links make a rapid A→B leave/enter pair even more likely than for adjacent cards. `hoveredEdgeId` feeds two things: `edgeHighlight()` treats the hovered relationship id exactly like `selectedEdgeId` (same "highlighted" stroke color/width), and a small `hoveredRelationship` lookup drives a new `isHoverEdgeEndpoint` flag on both endpoint employees' node data (a distinct indigo ring, ranked above chain-highlight/selection but below the transient drag-feedback states, in `EmployeeNode.tsx`'s existing precedence chain). Deliberately does *not* dim the rest of the chart — the recolored/thickened single link already stands out from its still-default-gray overlapping siblings without needing to mute everything else.

**The chart's initial fit is imperative, not the declarative `fitView` prop.** `<ReactFlow fitView>` only fits once, on React Flow's own mount — which happens before `employees`/`relationships` finish their async load, so it would fit an empty/stale node set and never refit once real data arrived (a chart that loads tiny or mis-cropped, inconsistently, depending on network timing). `OrgChartView.tsx` instead calls `instance.fitView()` itself inside a `useEffect` gated on both loading flags and `expandedNodeIds` being non-empty (i.e. the default-expand effect has already run), guarded by `hasAutoFitRef` so it only fires once per chart — reset when `currentOrgChartId` changes so switching charts re-fits instead of keeping the previous chart's pan/zoom.

**Hovering or pinning (clicking) a card highlights its full reporting chain.** `useReportingChain.ts` computes, for one "active" employee id, everyone to keep at full opacity (ancestors up the primary tree, any dotted/secondary managers plus *their* ancestor chain, the full descendant subtree, and anyone dotted-reporting directly to them) plus a narrower `chainIds` set used only to decide whether an *edge* counts as part of the chain. `useChartNodes.ts` combines `hoverEmployeeId` (local state) with `selectedEmployeeId` (from the store, persists until deselected) into one `activeEmployeeId` — hover takes priority while active, falling back to the pin once the mouse leaves. Clicking a card also opens `EmployeeDetailPanel.tsx` (manager/functional managers/direct reports/incoming functional reports, each row clickable to jump to that person) and pans the view to it (current zoom preserved via `getZoom()`, never forced) — but only on an actual selection change, never from toggling that same card's collapse or focus badge (`lastCenteredIdRef` in `OrgChartView.tsx` guards this).

**The mouseLeave→null transition is debounced (~120ms), not immediate** (`handleNodeMouseEnter`/`handleNodeMouseLeave` in `useChartNodes.ts`, fixed 2026-07-29). React Flow's per-node native `mouseenter`/`mouseleave` have no cross-node ordering guarantee — leaving card A and entering card B are two independent events with a real gap, and clearing `hoverEmployeeId` immediately on leave meant that gap rendered a frame with nothing highlighted, flickering visibly when the user hovered quickly across the chart. `clearHoverTimeoutRef` schedules the clear instead of applying it; `handleNodeMouseEnter` cancels any pending clear before setting the new id, so a fast A→B transition never dips through "nothing hovered." The `isReassigningEdgeRef`/`isDraggingRef` guards are re-checked **inside** the timeout callback too, not just at schedule time — a drag or edge-reassign can start during the 120ms window, and without the in-callback recheck the stale timeout would still null the hover mid-drag, reintroducing the flicker the same guards already prevent elsewhere (the `isDraggingRef`-gated sync effect a few lines below).

**Two independent collapse mechanisms per card, both round edge badges** (`CollapseBadge` in `EmployeeNode.tsx`). The bottom badge toggles the person's own entry in `expandedNodeIds` (downward: hide/show their subtree — the same set `useVisibleGraph` walks). The top badge toggles their entry in `focusedNodeIds` (upward "focus mode": hide everyone *except* this person and their already-visible subtree — ancestors and unrelated branches alike disappear). `focusedNodeIds` is a Set, so multiple people can be focused at once (the visible set becomes the union of each focused person's subtree); the filter only recurses into a child via `childrenOf` if that child is *already* in the expand-based visible set, so focus mode only ever hides, never force-reveals a separately-collapsed subtree.

**"+" buttons on chart nodes** (`EmployeeNode.tsx`, top-right/bottom-right corners) each open a small popover with two actions: create a brand-new employee and link them immediately (`quickAddManager`/`quickAddSubordinate` in `OrgChartView.tsx`), or link an existing employee via `LinkExistingEmployeeModal` (candidates filtered by `wouldCreateCycle`). When linking/creating a manager relationship, whether the new edge is primary is decided automatically: primary if the employee doesn't already have one, secondary otherwise. Double-clicking a node's first name, last name, poste, or department (same file) opens an inline editor (text input for name, a `<select>` sourced from `useJobTitles()`/`useDepartments()` for poste/department, matching the grid's catalog-only constraint) — a single click keeps its existing role of selecting the node.

**A double-click only opens that inline editor if the card was already selected before the gesture** (`startEdit` in `EmployeeNode.tsx`, guarded on `isSelected`, added 2026-07-30 after a user report). Without this, double-clicking a not-yet-selected card to select it could pop open a name/poste/department editor nobody meant to touch — the first click of a double-click also bubbles up and selects the card via React Flow's `onNodeClick`, so a double-click on a previously-unselected card used to both select AND edit in the same gesture. The guard works because of React's batching: both clicks and the `dblclick` fire synchronously within one browser task, so the `isSelected` value closed over by that render's event handlers is still the *pre-gesture* value for the whole gesture — `startEdit` sees `isSelected: false` and bails, even though the card visibly ends up selected once React flushes afterward. A second, separate double-click (now that a render has actually happened with `isSelected: true`) opens the editor normally. Verified live by dispatching a full synchronous click+click+dblclick sequence via `javascript_tool` and checking state before vs. after React settles — `computer.double_click`/`left_click` didn't reliably reach this node's click handling at all in this session (see [[feedback_browser_testing_gotchas]]), dispatched native `PointerEvent`/`MouseEvent` sequences did.

**The same guard applies to the Vendu/Réel assignment gauges** (the `<button title="Modifier les missions">` wrapping both `MetricRow`s, added same day as a follow-up). Unlike the text fields above, this one previously called `e.stopPropagation()` unconditionally on every click, so a single click on the gauges of a not-yet-selected card opened `AssignmentEditorModal` directly, without ever selecting the card. Fixed the same way: `if (!isSelected) return;` before `stopPropagation()`/`openAssignments()` — on an unselected card this returns early and deliberately does **not** call `stopPropagation()`, so the click bubbles up to `onNodeClick` and just selects the card, exactly like clicking anywhere else on it would. A second click, now that the card is selected, opens the modal.

**Employee photos live in a public Supabase Storage bucket** (`employee-photos`, `0010_employee_photos.sql`), referenced by `employees.photo_path`, with an interactive pan/zoom crop stored as `photo_zoom`/`photo_pan_x`/`photo_pan_y` (`0011_photo_reframe.sql`, phase 5b of the design handoff). `employeePhotoService.ts` is the only place that touches `supabase.storage` — upload (with image-type/5MB checks), delete, and `employeePhotoUrl()` (a `getPublicUrl` wrapper). `usePhotoActions.ts` composes that with the DB writes (`replacePhoto` uploads then best-effort-deletes the old object; `saveFrame` persists a crop; `deletePhoto` nulls `photo_path` and resets the crop). A new upload always resets `photo_zoom`/`photo_pan_x`/`photo_pan_y` to their defaults (`employeeService.ts`'s `updateEmployeePhoto`) since the old crop was framed for a different image.

`PhotoFrame.tsx` renders the cover-fit + pan/zoom crop from those three numbers via plain CSS (explicit width/height percentages sized from the image's aspect ratio, then `transform: scale(zoom) translate(panX%, panY%)`) — no canvas re-encoding. Because every percentage is relative to a *square* container's own size rather than absolute pixels, the identical (zoom, panX, panY) triple renders correctly at any avatar size (28px grid row, 36px chart card, 220px editor preview) — `baseSizePct()` in `lib/photoFrameMath.ts` is the one place that math lives, shared by `PhotoFrame` and `PhotoEditorModal`'s own drag/zoom clamping.

`PhotoAvatar.tsx` (used by both `EmployeeNode.tsx` and `EmployeeGrid`'s photo column) is purely presentational: a single click calls a stable `onOpen(employeeId)` callback owned by the parent (`OrgChartView`/`EmployeeGrid`), which opens one `PhotoEditorModal.tsx` — browse, drag-and-drop, paste (Ctrl+V), reframe, and delete all in one interface, rather than separate hover-revealed actions. Paste is caught with a `document`-level listener while the modal is mounted, not a listener on the small avatar itself — a non-editable focused element doesn't reliably receive native paste events in every browser, and requiring the avatar to hold focus was fragile in practice. `OrgChartView`/`EmployeeGrid` each hold `photoEditEmployeeId` locally and render one `PhotoEditorModal` for it; since `EmployeeGrid` owns its rows directly (a plain `<table>`, not a recycling grid library), the selection highlight is just a conditional class on the row's own render — nothing needs to force-remount cells to pick it up.

Per-employee assignments (client/mission + %ETP, one-to-many) are edited through the standalone `AssignmentEditorModal`, opened from a summary badge/cell in both the grid and the chart — not an expandable grid row.

**The left panel's 4 grids (Employés, Clients / Missions, Postes, Business Units) are hand-rolled tables, not a grid library** (backlog item 31 — AG Grid was fully retired 2026-07-29; `EmployeeGrid` migrated first, the 3 catalog grids followed the same day; see the backlog memory for the diagnostic that motivated it and the size win: ~1.7 MB → ~765 KB minified). Each is a plain `<table role="grid">` over a hook's live array, with inline editing built on two shared pieces in `src/components/grid/`:

- **`useEditableRows.ts`** is the editing state machine, generic over the row type and its field list. It owns: which cell is active, a "frozen" pre-edit snapshot of the row currently being edited (so `effectiveForSort` in `editableGridLogic.ts` keeps that one row pinned at its old sort position while the rest of the list sorts live — this is what replaced AG Grid's per-column sort comparator), and the local-only "draft" row created by "+ Ajouter" that is never written to Supabase until it has real content (`hasContentIn`, checked against each grid's own `requiredFields` — just `name` for the 3 catalog grids, `first_name`/`last_name` for employees). A grid supplies `createRow`/`updateField`; everything about *when* those fire — Tab to the next field and stop at the row's end (never wrap), Escape to cancel, a click anywhere else to commit — lives in this one hook, so there is exactly one implementation of the rules across all 4 grids. Deliberately only one place ever commits a field, `handleBlur`; keydown handlers never commit directly, they record an intent in a ref and force the blur themselves via `.blur()` — see the hook's own comments for why an earlier "commit + suppress next blur" design broke the moment a blur didn't reliably follow (Tab at the end of a row).
- **`EditableCell.tsx`** is the one cell renderer every grid uses: closed, a button that activates the cell on click; active, a plain `<input>` or `<select>` wired to the hook above. A field can override the closed-state `display` (only `department`'s colour dot and Clients/Missions' `type` label need this) and pass `options`/`allowEmpty` for a select (Poste/Business Unit allow a blank "—"; Clients/Missions' `type` does not, since the column is `NOT NULL`).

`useRowStabilizer.ts`, `lib/gridTheme.ts`, and the `data-row-stabilizer-ignore` attribute that used to mark modals as "not part of the grid" for AG Grid's click-outside detection are all gone — a plain `<table>` has no row-recycling or popup-parent machinery to fight, so there was nothing left needing that compensation layer.

**Left pane is tabbed** (`LeftPanel.tsx`, local `useState`, not in the Zustand store): Employés (`EmployeeGrid`), Clients / Missions (`ClientsMissionsGrid`), Allocations (`AllocationsView`, read-only, not an editable grid at all), Postes (`JobTitlesGrid`), Business Units (`DepartmentsGrid`). A density toggle (`Confortable`/`Compact`, see `uiPreferencesStore.ts` above) sits alongside the tabs and applies to all 4 grids at once. `ClientsMissionsGrid` and `JobTitlesGrid` are standalone catalog editors for tables that also back other features — `clients_missions` feeds `AssignmentEditorModal`'s autocomplete, `job_titles` feeds the "Poste" column's options in `EmployeeGrid` (sourced live from `useJobTitles()`). `job_titles` has no FK from `employees.job_title` — it's a curated suggestion list enforced only at the UI layer (select-only, no free text), so deleting a job title never cascades or blocks. `clients_missions` does have a real FK from `assignments` (`on delete restrict`), so `ClientsMissionsGrid`'s delete handler must catch and surface that failure.

**Department colors are computed by palette position, overridable per-row via a stored `color` column** (`0014_department_color.sql`, added 2026-07-29 — nullable, no backfill). `departmentColor.ts`'s `departmentColorMap` is `d.color ?? PALETTE[i % PALETTE.length]` — a department keeps its old palette-by-creation-order color until someone explicitly picks one via `DepartmentsGrid.tsx`'s swatch. The picker is a visually-hidden native `<input type="color">` behind the visible dot (`ColorSwatch`, same file) — deliberately binds a native `change` listener via a ref rather than React's `onChange` prop, since React normalizes `onChange` to the native `input` event for a color field, which fires continuously while the user drags inside the OS picker, not just once on commit; using it directly would push an undo/redo entry (and a Supabase write) per drag frame instead of once when the picker closes. `useDepartments.ts`'s `updateDepartmentColor` has no `oldNameHint`-style parameter the way `updateDepartment`/`updateJobTitle` do — that pattern exists solely to compensate for AG Grid mutating row data in place before firing its change event, which doesn't apply here. **The hidden input must never be sized `h-0 w-0`** (a real zero-size element, as it initially shipped) — Chrome silently refuses to open the native color picker for a genuinely zero-dimension `<input type="color">`, clicking the dot does nothing, no error anywhere (caught 2026-07-29 from a user report). Fixed to the standard visually-hidden-but-interactive sizing instead: `absolute h-px w-px overflow-hidden opacity-0` (1×1px, not 0×0).

**`src/lib/database.types.ts` is still hand-authored** and must be kept in sync with `supabase/migrations/*.sql` by hand until someone runs the generator. It was audited against every migration up to `0013` on 2026-07-26 and had **no drift** — including that `set_updated_at`/`set_audit_fields`/`prevent_reporting_cycle` are trigger functions and so correctly absent from `Functions`, which lists only the `duplicate_org_chart` RPC. It must satisfy the `GenericSchema` shape from `@supabase/supabase-js` (each table needs `Relationships: []`, the schema needs `Views`/`Functions`) or the client's generic inference silently degrades and `.insert()`/`.update()` calls fail to typecheck.

`npm run gen:types` (`scripts/gen-types.mjs`) replaces it from the live schema. It reads the project ref out of `.env.local`'s `VITE_SUPABASE_URL`, so there is nothing to configure, and reaches the schema one of two ways:

```bash
SUPABASE_DB_URL='postgresql://...' npm run gen:types
```

**That route requires docker or podman**, which is the non-obvious part: `supabase gen types --db-url` does not connect to Postgres directly, it spawns a containerised `postgres-meta` image. On a machine with no container runtime it fails as `NotFound: ChildProcess.spawn (podman run …)`, which reads like a network or credential problem and is neither. Its upside is real when a runtime is available — scoped to this single database, no account token at all, and the env var keeps the password off disk (`.env.local` is also read if you'd rather keep it there). Use the dashboard's **Session pooler** string, not "Direct connection" — the latter is IPv6-only, the same trap the backup workflow documents.

**Without `SUPABASE_DB_URL` the script uses `--project-id` and the Management API, which needs nothing installed** — this is the route that works on a stock machine, and in practice the one to use here. It does need `npx supabase login` (or `SUPABASE_ACCESS_TOKEN`), and that is an **account-level** token: it grants the CLI access to every organization and project the account can see, since Supabase Personal Access Tokens cannot be scoped to one project. `npx supabase logout` straight after generating limits the window.

The script captures **both** of the CLI's output streams (it reports failures on stdout, not stderr) and **masks the password** out of them before printing: the CLI echoes the full connection string in the `podman run --env PG_META_DB_URL=…` command line it is about to spawn, which leaked a real password into a pasted error report once. It also rejects a connection string still carrying a placeholder (`REGION`, `[YOUR-PASSWORD]`) before calling the CLI at all, and maps the three real failure modes — no container runtime, unresolvable host, not authenticated — to distinct hints.

The script buffers and validates the CLI's output before writing, deliberately: a plain `supabase gen types ... > src/lib/database.types.ts` truncates the target *before* the CLI runs, so any failure (not authenticated, no network, wrong ref) leaves an empty types file and a build error pointing nowhere near the cause. Only `supabaseClient.ts` imports from this file (just `Database`), so a full regeneration is a safe drop-in replacement.

**`OrgChartView` is wrapped in an `ErrorBoundary`** (`src/components/shared/ErrorBoundary.tsx`, mounted in `AppShell.tsx`) — the only error boundary in the app. Without it, a render-time throw anywhere in the chart subtree unmounts it with no visible trace (React only logs to console), which reads as the chart silently "disappearing" rather than a diagnosable bug. Add a boundary around any other subtree where the same silent-blank-panel failure mode would be hard to notice.

**Library version notes:** Tailwind is v4, configured via the `@tailwindcss/vite` plugin in `vite.config.ts`, not a `tailwind.config.js`/PostCSS setup. There is no grid library dependency at all — `ag-grid-community`/`ag-grid-react` were removed from `package.json` when the last 3 grids moved off AG Grid (item 31, 2026-07-29); don't reintroduce one for a new grid without checking whether `useEditableRows.ts`/`EditableCell.tsx` already cover the need. The chart runs on **`@xyflow/react` v12** (migrated from the old `reactflow` v11 package, 2026-07-30, backlog item 32) — import from `@xyflow/react`, not `reactflow`. Two things the migration required beyond a straight import swap: `EmployeeNodeData`/`ReportingEdgeData` (`EmployeeNode.tsx`/`ReportingEdge.tsx`) now `extends Record<string, unknown>`, since v12's `Node<T>`/`Edge<T>` generics require their data shape to satisfy that constraint; and `NodeProps`/`EdgeProps` now take the *whole* `Node<T>`/`Edge<T>` type as their generic argument, not just the data shape (`NodeProps<Node<EmployeeNodeData>>`, not `NodeProps<EmployeeNodeData>`). `@xyflow/react` bundles its own internal `zustand@4.5.7`, independent of and unrelated to the app's own `zustand@^5.0.14` used for `selectionStore`/`historyStore`/etc. — no conflict, they're separate dependency trees. If the dev server ever throws `ENOENT ... node_modules/reactflow/...` after a dependency swap like this one, it's Vite's stale `node_modules/.vite` dependency-optimizer cache, not a real error — delete that directory and restart the dev server. The chart's layout engine is **elkjs**, not dagre (`dagre`/`@types/dagre` removed from `package.json` 2026-07-30, backlog item 32) — imported as `elkjs/lib/elk.bundled.js` specifically, which runs in-thread via a Promise rather than a real Web Worker, so no worker-file/bundler config was needed at this app's scale. See CLAUDE.md's "elk lays out every employee..." note above for the async-layout and sibling-reorder implications this swap had.

## Deployment

Production: https://orgchart-dun.vercel.app, deployed by Vercel from `Havas-International-Paris/OrgChart` on GitHub — every push to `main` auto-deploys, no manual step. No separate staging environment: the same Supabase project backs both local dev and production. New SQL migrations must be applied by hand to that one project (see README.md's "Déploiement et mise à jour" section) — there's no automated migration pipeline.

**GitHub Actions + Supabase Postgres gotchas** (hit both when setting up `.github/workflows/supabase-backup.yml`, now documented inline in that file too):
- Supabase's "Direct connection" string (`db.<ref>.supabase.co`) is **IPv6-only**; GitHub's hosted runners have no IPv6 egress and fail with `Network is unreachable`. Use the **Session pooler** connection string instead (`aws-0-<region>.pooler.supabase.com`, found via the Connect modal's "Direct" tab).
- `pg_dump` refuses to dump from a server newer than itself. Supabase currently runs Postgres 17, but Ubuntu's default `postgresql-client` package is older — install `postgresql-client-17` from the official PGDG apt repo and invoke it by full path (`/usr/lib/postgresql/17/bin/pg_dump`), since the older bundled one stays first on `PATH`.
- The three repo secrets (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_DB_URL`) have similar names — easy to edit the wrong one via GitHub's secrets UI (it happened once already). `SUPABASE_URL` must stay a plain `https://` URL (used by the keep-alive ping *and* by the backup's photo download step); the Postgres connection string belongs only in `SUPABASE_DB_URL`.

**The backup covers Storage as well as Postgres.** The `employee-photos` bucket is archived alongside the `pg_dump`, driven by the `photo_path` values in `employees` rather than by listing the bucket — that is exactly the set of objects a restore of the same dump would need, it requires no Storage credentials (the bucket is public), and any orphaned object in the bucket is by definition not worth restoring. Object keys are preserved inside `photos-<date>.tar.gz` so a restore can put them back at the same paths. A referenced object that 404s is recorded in `photos-missing.txt` and does not fail the run (it is already a broken reference in production, and aborting would lose the photos that *are* fine), but a `psql` failure fails the step outright rather than silently producing an empty photo archive.

## Known issues

- No optimistic locking: if two users edit the same field at the same moment, last write wins silently.
- No granular roles — every authenticated user can edit or delete anything.
- No automated test coverage beyond the pure-logic modules. `npm test` (Vitest, `vitest.config.ts`, node environment — no jsdom) covers `layoutEngine`, `useVisibleGraph`, `useReportingChain`, `wouldCreateCycle`, `etpStatus`, `departmentColor`, `photoFrameMath`, and the grid editing logic in `editableGridLogic.ts`; everything involving React rendering, grid interaction, React Flow interaction or Supabase I/O is still verified only by hand. `useVisibleGraph`/`useReportingChain` each expose their body as a plain `compute*` function precisely so the hook can be tested without React — keep that split if you touch them, and don't inline the logic back into the `useMemo`.
**`?e2e=1` puts the app in test mode** (`src/lib/e2eMode.ts`), and the authenticated specs navigate to it. It hides the overlays drawn on top of the React Flow canvas — `DepartmentLegend`, `MiniMap`, `Controls`, the export `Panel` — and makes `setCenter`'s pan instant instead of 400ms. Undo/redo buttons stay, since the specs click them. This exists because the canvas was otherwise not reliably clickable under automation: Playwright named the department legend outright as *intercepting pointer events* on cards beneath it, and a still-moving viewport meant clicks were attempted against travelling targets — the two interaction specs failed about half the time until this landed, then passed six runs straight. It is a query parameter rather than a `VITE_*` env var on purpose: the dev server is shared with manual use here, so a build flag would change what the developer sees in their own browser. **It changes no data path, mutation or undo behaviour** — if you extend it, keep that true, or the suite stops testing the real app.

- The E2E suite runs end to end now (login, throwaway-chart provisioning, isolation assertion, teardown), and **covers the compound undo/redo path** (quick-add a subordinate → undo → redo, driven through the chart's buttons). The setup seeds one root employee directly via `supabase-js` rather than through the UI, predating item 31's AG Grid removal — driving the old AG Grid cell editor asynchronously wasn't reliable (typing after Enter produced `Ca` instead of `Camille` on one run and did not open at all on the next). Specs therefore drive the chart's own buttons. Still uncovered: anything that needs grid cell editing — worth retrying now that the grids are plain `<input>`/`<select>` elements rather than an AG Grid popup editor, but not yet attempted. A manual pass after item 31's migration hit a related but distinct issue: this session's browser-automation tool's synthetic `Enter`/`Tab` keydown does not reliably reach React's handlers (a real click elsewhere, which fires a genuine DOM blur, commits correctly every time) — see [[feedback_browser_testing_gotchas]].
